# 云端连接与 401 排查记录

日期：2026-10-09。基于本地 `inspiration-drawer` 8.0.21 与相邻 `inspiration-wallet-server` 工作区。保留此前工作流和窗口诊断修改；本轮没有推送、部署、打包或修改生产配置。

## 用户现象与判断边界

用户反馈可以登录，但获取服务端模型失败，生图出现 401，各步骤都可能卡住。尚未取得故障用户的完整错误、认证响应、原生诊断日志或服务端拒绝记录，不能认定所有受影响用户具有同一根因。

当前服务端代码中，`/v1/ai/images/models` 先检查客户端 JWT 和数据库会话。该接口真正返回 HTTP 401 时，优先排查客户端凭证或会话；它还未调用生图供应商。供应商生图接口返回 401 时，服务端会转换为 HTTP 502、`provider_auth_failed`，提示管理员检查渠道密钥。错误文案中的“401”与请求实际 HTTP 状态需要区分。

邮箱登录接口不需要旧访问令牌；界面也能显示上一次成功缓存的账户资料。因此登录成功或余额可见，不足以证明后续受保护接口的鉴权正常。

## 已确认的代码问题与本地修复

1. **登录没有替换内存中的旧访问令牌。** 验证邮箱登录成功后保存了授权文件，却未立即保存返回的新令牌。现将授权文件与新令牌在同一写锁中更新。
2. **令牌缓存使用固定 12 分钟，未读取真实有效期，也未关联当前授权。** 现按服务器的 `accessTokenExpiresIn`、JWT 的 `exp` 和 HTTPS `Date` 头缩短缓存，预留刷新余量，以单调时钟计时；不依赖用户电脑的系统时间。解码 JWT 仅用于缩短缓存和避免长任务跨账号查询，不能代替服务端验证。旧响应无 Date 时兼容使用 `exp-iat`；完全没有有效期信息时保持原缓存上限并预留余量。
3. **长任务一直使用提交时的令牌。** 任务最长查询 12 分钟，而提交时的令牌本身可能已缓存很久。现在每次已有的状态 GET 之前取得当前令牌；过期时使用原邮箱同步路径更新凭证，不重新提交任务。账号切换后停止查询并保留原任务映射，提示切回原账号接管。
4. **收到 401 后仍保留坏令牌。** 云端受保护接口收到 401 时只淘汰该请求所用的缓存令牌；旧请求的迟到 401 不会清除新登录的令牌。当前请求失败照常返回，不自动重放生图或任务提交。任务查询的 401 保留任务映射，便于重新登录后接管。
5. **不同登录状态共用同步请求，旧同步响应可能覆盖新登录。** 同步合并按当前授权内容的内部 SHA-256 标识隔离；落盘前检查请求开始时的授权仍然相同。旧账号失效响应也不能删除随后登录的新账号授权。这个标识不写日志。

没有改动生成并发、模型映射、计费、现有网络重试条件或请求超时。没有自动 reload 或自动重新生成。

## 新增诊断

客户端继续使用原生诊断的轮转 JSONL 文件：

`%LOCALAPPDATA%\com.inspirationdrawer.app\logs\renderer-diagnostics.jsonl`

单文件最多 2 MiB，当前文件与两份轮转文件总计约 6 MiB。日志不会自动上传，渲染器退出后仍可保留。

新增事件：

| 事件 | 用途 |
| --- | --- |
| `cloud_token_received` | 缓存有效期、是否取得服务器时间；不记录令牌 |
| `cloud_auth_rejected` | 操作类别、HTTP 401、是否淘汰对应缓存；明确没有自动重放 |
| `cloud_transport_failure` | 标准云端传输入口的 DNS/连接/TLS/代理/超时等类别、路径选择、耗时、是否进入原有回退 |
| `cloud_http_response` | 标准云端入口的失败 HTTP 响应、慢响应或回退响应 |
| `cloud_response_failure` | 授权/账户/模型及任务响应读取失败、超时或 JSON 解码失败的类别 |

操作名称使用固定白名单，不记录 URL 查询参数、任务 ID、原始异常内容、请求体、图片、提示词、令牌或用户完整路径。传输错误分类采用当前错误链的特征，属于诊断提示，不是抓包得到的网络根因。普通云端入口与 Agent 的 401 均有诊断；没有声称每一个 BYOK、下载或灵感空间请求都已覆盖这些新增事件。

服务端 `src/plugins/jwt.ts` 新增 `access_token_rejected` 警告，区分凭证缺失、过期、验证失败、claims 无效、会话不存在/撤销/过期、账号或授权失效。保留原 401 返回格式及所有鉴权校验，不记录 JWT、邮箱、用户/授权/会话 ID。签名、issuer 和 audience 等验证失败目前仍归为 `token_verification_failed`，不能根据这一类别断言是哪一种生产配置问题。服务端使用现有 logger，未改变生产 Docker 日志配置；上述 6 MiB 上限指客户端本地诊断文件。

## 仍需证据的静态风险

- 多个云端调用每次新建 HTTP Client，跨请求连接复用不足，可能放大 DNS/TLS 成本；本轮没有改连接池策略，不能将它认定为 401 根因。
- 账户/生图、Agent、灵感空间的代理选择存在差异。手工代理 URL 含 `=` 时可能被旧规范化逻辑误认为 Windows 协议列表；`ALL_PROXY`、`NO_PROXY`、Windows bypass/PAC 的处理也未统一。本轮没有改变这些路由或回退规则。
- 失败后模型自动刷新仍有既有节奏（进入画布、窗口 focus、五分钟轮询或手动刷新）；本轮没有通过增加自动重试来掩盖鉴权失败。
- 生产 JWT 密钥、issuer、有效期、会话状态，以及多实例配置一致性未检查；未读取生产 `.env`。
- 用户实际的 DNS/TLS/代理错误，或反向代理返回的 401，需要客户端安全诊断与对应时间的服务端日志确认。应先确认实际 HTTP 状态和错误码，再决定下一步修复。
